## 1. 系统定位

好友系统解决的是“两个玩家之间如何建立关系、删除关系，以及如何看到对方在线状态”的问题。

它的核心不是复杂组织结构，而是：

- 双向确认
- 双向持久化
- 好友列表同步
- 在线状态变化通知

### 1.1 主要参与者

#### 1.1.1 客户端

## 2. 客户端好友交互链路

### 2.1 本地状态组织

客户端 `FriendManager` 很轻，主要维护：

- `allFriends`

这说明好友系统的大部分交互逻辑并不在 Manager，而是更多放在 Service 和 UI 里。

### 2.2 添加好友流程

客户端添加好友主链路：

```text
UIFriends 输入好友名称或 ID
  -> FriendService.SendFriendAddRequest
  -> 服务端转发给目标玩家
  -> 目标玩家客户端 OnFriendAddRequest
  -> 弹确认框
  -> 同意/拒绝后 SendFriendAddResponse
```

### 2.3 为什么客户端要弹框后再回包

`FriendService.OnFriendAddRequest()` 收到请求后，不会立刻答应，而是：

- 弹 `MessageBox`
- 给 `OnYes / OnNo` 绑定 Lambda 回调
- 等玩家点击后再发响应

这其实就是一个典型的：

> **异步交互确认模型。**

### 2.4 UIFriends 的职责

`UIFriends` 不只是展示好友，还承担多个入口：

- 添加好友
- 私聊好友
- 邀请组队
- 发起竞技场挑战
- 删除好友

这说明好友列表其实是多个社交功能的枢纽入口。

## 3. 服务端好友关系处理

### 3.1 FriendService 的职责

服务端 `FriendService` 负责三类请求：

- `FriendAddRequest`
- `FriendAddResponse`
- `FriendRemoveRequest`

### 3.2 添加好友请求的处理逻辑

当服务端收到加好友请求时，会先做几步处理：

1. 如果只传了名字，就尝试把名字解析成目标 ID
2. 检查是不是已经是好友
3. 检查目标玩家是否在线
4. 把请求转发给目标玩家

也就是说当前好友申请链路是：

> **强在线依赖的实时转发模型。**

### 3.3 好友接受后的真正生效点

当目标玩家同意后，服务端会：

- 找到请求方在线会话
- 调用双方各自的 `FriendManager.AddFriend()`
- 双边都写入好友关系
- 保存数据库
- 回包给双方

所以好友关系生效不是单边改，而是：

> **两边同时落库、两边同时生效。**

### 3.4 删除好友流程

删除好友时，服务端会：

- 先删除当前角色自己的好友关系
- 如果对方在线，则同步删除对方好友关系中的自己
- 如果对方不在线，则直接操作数据库删掉那条关系

这说明删除流程考虑了在线和离线两种情况，比添加流程更完整一些。

## 4. 好友列表与在线状态同步

### 4.1 服务端 FriendManager 的角色

服务端 `FriendManager` 是挂在 `Character` 身上的组件型管理器。

它负责：

- 初始化角色好友列表
- 生成 `NFriendInfo`
- 更新好友在线状态
- 在后处理阶段把最新好友列表写进响应包

### 4.2 在线状态是怎么更新的

`GetFriendInfo()` 在构造好友信息时，会尝试通过 `CharacterManager.Instance.GetCharacter(friendId)` 找在线角色：

- 找到：状态记为在线
- 找不到：状态记为离线

而且还会反向通知对方 `UpdateFriendInfo()`，所以好友状态带有双向联动特征。

### 4.3 客户端列表刷新入口

客户端 `FriendService.OnFriendList()` 收到 `FriendListResponse` 后，会：

- 更新 `FriendManager.Instance.allFriends`
- 触发 `OnFriendUpdate`
- `UIFriends` 再重新刷新列表

所以好友列表刷新整体上是：

> **服务端生成最新列表，客户端做全量覆盖刷新。**

## 5. 当前实现的边界与风险

### 5.1 添加好友强依赖对方在线

当前添加好友如果对方不在线会直接失败，没有离线申请邮箱或延迟确认机制。

### 5.2 客户端 Manager 偏轻

`FriendManager` 只有列表存储，很多交互状态都散落在 `FriendService` 和 `UIFriends` 中。项目变大后，这会让入口不够集中。

### 5.3 名称查找效率与唯一性要关注

如果通过名字加好友，服务端会遍历在线角色列表找匹配名称。在线人数大时，这种方式效率和唯一性都要关注。

### 5.4 删除逻辑里的参数语义要小心

删除好友时既传关系 ID 又传好友角色 ID，调用方和服务端要始终明确两者差异，否则容易删错对象。

---

## 6. 总结

好友系统可以压缩成一句话：

> **好友系统本质上是一个“在线转发请求 + 双向确认 + 双边关系同时落地”的关系管理系统，客户端用列表展示结果，服务端负责真实好友关系和在线状态更新。**

复盘时建议重点讲清三点：

1. 为什么加好友必须有“请求方 + 被请求方”双向确认
2. 为什么好友关系生效要两边一起改
3. 为什么好友列表看起来简单，但它其实是多个社交功能的入口枢纽
