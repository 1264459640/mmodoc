## 1. 系统定位

组队系统解决的是“临时多人会话如何建立、同步和解散”的问题。

和公会相比，组队更轻、更短生命周期，也更依赖在线实时交互。

它的核心特点是：

- 邀请制
- 强在线依赖
- 临时状态
- 全量队伍信息同步

## 2. 客户端组队交互链路

### 2.1 邀请流程

客户端邀请组队一般从好友列表发起：

```text
UIFriends 点击邀请组队
  -> TeamService.SendTeamInviteRequest
  -> 服务端转发给目标玩家
  -> 目标玩家客户端 OnTeamInviteRequest
  -> 弹确认框
  -> TeamService.SendTeamInviteResponse
```

### 2.2 接收邀请的处理方式

和好友系统一样，客户端收到组队邀请时不会直接同意，而是通过确认框等待玩家选择。

因此组队系统也是标准的：

> **请求转发 + 本地确认 + 再回包** 模型。

### 2.3 TeamManager 的职责

客户端 `TeamManager` 比较轻，最核心的方法是：

- `UpdateTeamInfo(NTeamInfo team)`

它会：

- 把最新队伍数据写到 `User.Instance.TeamInfo`
- 决定主界面队伍 UI 是否显示

这说明客户端并没有额外建复杂的队伍本地模型，而是直接围绕协议对象工作。

### 2.4 UITeam 的职责

`UITeam` 主要负责：

- 显示成员数量
- 显示每个成员信息
- 区分队长
- 发起退出队伍请求

所以它是纯表现层，不负责真正的组队状态维护。

## 3. 服务端队伍生命周期

### 3.1 TeamManager 的作用

服务端 `TeamManager` 维护：

- `Teams`
- `CharacterTeams`

以及提供：

- 根据角色查找队伍
- 给队长和新成员组建/扩展队伍

### 3.2 队伍创建逻辑

`AddTeamMemBer()` 的逻辑是：

- 如果队长当前没有队伍，就先创建一个 `Team`
- 再把新成员加进去

也就是说，队伍不是显式“先点创建”，而是在第一次邀请成功时隐式创建。

### 3.3 Team 模型的职责

服务端 `Team` 负责：

- 维护队长和成员列表
- 加成员
- 成员离队
- 在后处理阶段生成 `TeamInfoResponse`

所以它是组队系统真正的领域状态对象。

### 3.4 退出队伍流程

当客户端发 `TeamLeaveRequest` 后，服务端会：

- 找到当前角色
- 调用 `character.Team.Leave(character)`
- 更新队长或清空队伍
- 回包成功

从 `Team.Leave()` 可以看到：

- 如果离开的是队长，则把队长交给第一个剩余成员
- 如果没有剩余成员，则队伍变为空

## 4. TeamInfo 同步方式

### 4.1 客户端接收方式

客户端 `TeamService.OnTeamInfo()` 收到 `TeamInfoResponse` 后，直接调用：

```text
TeamManager.Instance.UpdateTeamInfo(message.Team)
```

### 4.2 这种同步方式的特点

它不是对本地成员做增删改，而是：

> **收到一份新的 `NTeamInfo`，然后整体覆盖当前队伍状态。**

这种做法的优点是：

- 简单
- 不容易出现局部状态残留
- UI 刷新逻辑直接

但缺点也很明显：

- 不够增量化
- 队伍状态复杂后会更依赖整包同步

### 4.3 为什么组队适合这种方式

因为当前队伍规模小、生命周期短，用整包 `TeamInfo` 覆盖比做复杂增量同步更划算。

## 5. 当前实现的边界与风险

### 5.1 组队强依赖在线状态

当前邀请组队时，如果对方不在线就直接失败，没有离线邀请承接。

### 5.2 服务端前置校验仍较轻

代码里明确写了 `TODO:执行一些前置数据效验`，说明：

- 距离限制
- 地图限制
- 组队人数上限
- 重复邀请等

还有继续补强空间。

### 5.3 CharacterTeams 字典当前利用度要继续观察

服务端 `TeamManager` 里有 `CharacterTeams`，但从当前片段里看，核心维护逻辑更多还是通过 `Character.Team` 直接关联，字典的维护与利用需要继续核查。

### 5.4 空队伍回收策略需要关注

`Team` 为空后虽然队长会变成 null，但全局 `Teams` 列表里空队伍的复用和清理策略要持续关注。

---

## 6. 总结

组队系统可以压缩成一句话：

> **组队系统本质上是一个“在线邀请确认 + 服务端临时 Team 对象维护 + 客户端整包 TeamInfo 覆盖显示”的临时多人会话系统。**

复盘时建议重点讲清三点：

1. 为什么组队系统比公会更适合用轻量状态同步
2. 为什么组队邀请和好友申请在交互模型上很像
3. 为什么 `Team` 适合做服务端的临时领域对象
