# 社交系统速记卡（3 分钟版）

## 1. 一句话总述

> 这套社交系统本质上是 **“客户端 Manager 组织本地社交状态 + Service 负责请求/转发桥接 + 服务端维护真实关系与组织对象”** 的多人交互系统。

---

## 2. 先背这 5 句话

1. **聊天系统管消息分流，好友系统管双边关系，组队系统管临时会话，公会系统管持久组织。**
2. **社交系统最常见的链路是“我发请求 -> 服务端转给别人 -> 别人确认 -> 服务端落状态”。**
3. **聊天里的私聊和群聊不是同一种分发模型。**
4. **组队偏临时和轻量，公会偏持久和权限化。**
5. **客户端负责交互和展示，真实社交结果最终以后端状态为准。**

---

## 3. 30 秒讲清整体架构

### 3.1 五层结构

- **UI 层**：`UIChat / UIFriends / UITeam / UIGuild`
- **客户端管理层**：`ChatManager / FriendManager / TeamManager / GuildManager`
- **客户端服务层**：`ChatService / FriendService / TeamService / GuildService`
- **服务端服务层**：对应四个社交 Service
- **服务端状态层**：`ChatManager / FriendManager / TeamManager / GuildManager / Guild / Team`

### 3.2 一句话理解

> **UI 发起操作，Manager 组织本地状态，Service 负责收发与转发，服务端再维护真实关系、消息池和组织对象。**

---

## 4. 60 秒讲清四条主链路

### 4.1 聊天链路

```text
UIChat 输入消息
  -> ChatManager.SendChat
  -> ChatService.SendChat
  -> 服务端 ChatService.OnChat
  -> 私聊直推 / 群聊入消息池
  -> ChatResponse
  -> ChatManager.AddMessages
  -> UIChat 刷新
```

压缩一句话：

> **私聊走在线直推，其他频道走消息池分流。**

### 4.2 好友链路

```text
A 发起加好友
  -> 服务端转发给 B
  -> B 客户端弹确认框
  -> B 回应同意/拒绝
  -> 服务端双边建立好友关系
  -> 双方收到结果与列表更新
```

压缩一句话：

> **好友系统是典型的双向确认、双边落地。**

### 4.3 组队链路

```text
A 邀请 B 组队
  -> 服务端转发给 B
  -> B 确认
  -> 服务端创建/更新 Team
  -> 推 TeamInfo
  -> 客户端覆盖更新队伍信息
```

压缩一句话：

> **组队系统是临时 Team 对象 + TeamInfo 全量覆盖同步。**

### 4.4 公会链路

```text
玩家申请加入公会
  -> 服务端记录申请
  -> 转发给会长
  -> 会长审批
  -> Guild 执行审批结果
  -> 更新公会成员与 GuildInfo
  -> 客户端刷新公会界面
```

压缩一句话：

> **公会系统是持久化组织 + 审批流 + 管理命令。**

---

## 5. 最容易被追问的 4 个点

### 5.1 为什么聊天要做频道位运算过滤

- 一个消息可能被多个显示标签消费
- 位掩码比大量 if-else 更紧凑
- 过滤逻辑统一且高效

### 5.2 为什么好友/组队/公会申请交互很像

- 都是 A 请求 B
- B 本地确认
- 服务端根据结果落状态
- 本质上都是多人交互审批流

### 5.3 为什么组队和公会不能用同一套模型

- 组队是临时状态，人数少，变化频繁
- 公会是持久组织，带权限、公告、审批、职位
- 二者生命周期和复杂度完全不同

### 5.4 客户端是不是社交状态真相源

不是。

- 客户端只做输入、展示和临时状态组织
- 真实好友关系、队伍成员、公会成员、聊天分发都以后端处理结果为准

---

## 6. 当前实现边界只记这 4 点

1. **很多社交交互强依赖目标在线**，离线承接较弱。
2. **聊天消息池清理策略要持续关注**，长期运行要考虑上限和回收。
3. **组队和公会更多依赖全量信息覆盖刷新**，简单但不够增量化。
4. **公会管理与聊天发言的服务端权限校验还值得继续强化。**

---

## 7. 最后 20 秒复盘模板

如果要快速收口，可以直接按这段说：

> 社交系统整体分成聊天、好友、组队、公会四块。聊天系统主要解决频道分流和消息显示，私聊走在线直推，群聊走消息池；好友系统是双向确认和双边关系建立；组队系统是临时 Team 对象配合 TeamInfo 同步；公会系统是持久化组织，带申请审批和管理命令。客户端 Manager 负责组织本地显示状态，Service 负责请求和转发桥接，真正的社交结果以后端状态为准。
