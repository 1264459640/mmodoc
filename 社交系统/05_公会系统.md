## 1. 系统定位

公会系统解决的是“长期存在的玩家组织如何创建、加入、管理和同步”的问题。

它和组队系统最大的差别在于：

- 公会是持久化组织
- 有领导者和职位
- 有申请审批
- 有公告和成员管理

所以它比组队系统更接近完整的组织管理系统。

## 2. 客户端公会交互链路

### 2.1 GuildManager 的职责

客户端 `GuildManager` 维护：

- `guildInfo`
- `myMemberInfo`
- `HasGuild`

并且封装了一个很实用的入口：

- `ShowGuild()`

它会根据是否已有公会决定：

- 打开无公会弹窗
- 还是直接打开公会主界面

这说明公会系统在客户端已经把“有无公会的 UI 分支”收敛到了 Manager 层。

### 2.2 创建公会流程

客户端创建公会主链路：

```text
输入公会名和公告
  -> GuildService.SendGuildCreate
  -> 服务端 GuildService.OnGuildCreate
  -> GuildManager.CreateGuild
  -> 返回 GuildCreateResponse
  -> 客户端 GuildService.OnGuildCreate
  -> GuildManager.Init(response.guildInfo)
```

### 2.3 申请加入与审批流程

客户端申请加入某个公会：

```text
GuildService.SendGuildJoinRequest(guildId)
  -> 服务端记录申请
  -> 转发给会长
  -> 会长客户端弹确认框
  -> SendGuildJoinResoinse
  -> 服务端批准/拒绝
  -> 返回结果给申请人
```

这说明公会申请流程和好友/组队一样，也属于“转发请求 + 本地确认 + 再回包”。

### 2.4 UIGuild 的职责

`UIGuild` 主要负责：

- 显示成员列表
- 显示公会基础信息
- 根据自己职位控制管理面板显示
- 发起踢人、晋升、罢免、转会长、修改公告等操作

所以它是典型的组织管理后台式 UI。

## 3. 服务端公会状态与领域对象

### 3.1 GuildManager 的职责

服务端 `GuildManager` 是全局单例，负责：

- 服务器启动时从数据库加载所有公会
- 维护 `Guilds` 字典
- 校验公会名是否存在
- 创建公会
- 返回公会列表信息

这说明公会在服务端属于：

> **全局持久化组织对象。**

### 3.2 Guild 对象的职责

真正承载业务细节的并不是 `GuildManager`，而是 `Guild` 领域对象。

`Guild` 负责：

- 处理入会申请
- 审批申请
- 添加成员
- 删除成员
- 生成 `NGuildInfo`
- 处理管理命令

所以可以理解成：

- `GuildManager` 管“有哪些公会”
- `Guild` 管“某个公会内部如何运作”

### 3.3 GuildInfo 的同步语义

`Guild.GuildInfo(Character from)` 会根据请求者身份决定返回的信息范围：

- 普通成员能看到成员列表
- 会长还能看到申请列表

这说明同一个公会对象，对不同角色暴露的信息深度可以不同。

## 4. 申请审批与管理命令

### 4.1 入会申请处理

当服务端收到 `GuildJoinRequest` 时，会：

1. 找到目标公会
2. 将当前角色信息补进 `Apply`
3. 调用 `guild.JoinApply()`
4. 如果会长在线，则把申请转发给会长

### 4.2 审批处理

当会长回复 `GuildJoinResponse` 时，服务端会：

- 调用 `guild.JoinAppove()`
- 如果同意，则把申请人加入公会
- 更新申请人角色上的公会归属
- 返回结果给申请人

### 4.3 管理命令的统一封装

客户端通过 `GuildService.SendAdminCommand()` 发出：

- 踢人
- 晋升
- 罢免
- 转让会长
- 修改公告

服务端再统一交给：

```text
character.Guild.ExexuteAdmin(...)
```

这说明公会管理操作已经形成：

> **统一命令入口 + 领域对象执行** 的结构。

## 5. 当前实现的边界与风险

### 5.1 公会管理权限校验粒度要继续确认

从客户端 UI 上已经做了部分职位判断，但服务端 `OnGuildAdmin()` 是否对每种命令都做了足够细的权限校验，还需要继续严格核查。

### 5.2 会长离线时的申请处理链路有限

当前公会申请主要依赖会长在线后收到转发请求，如果要做更完整的审批体验，后续可能需要离线申请箱或上线提醒机制。

### 5.3 管理命令执行细节还可继续补强

例如 `Kickout` 在 `ExexuteAdmin()` 中目前还是占位式处理思路，说明部分公会管理细节还未完全闭环。

### 5.4 客户端刷新更多依赖全量 GuildInfo

公会变化后客户端主要依赖新的 `GuildInfo` 做初始化与刷新，简单直接，但后续如果成员很多、申请很多，增量同步会更高效。

---

## 6. 总结

公会系统可以压缩成一句话：

> **公会系统本质上是一个“全局持久化组织管理 + 会长审批流 + 统一管理命令入口 + 客户端全量 GuildInfo 展示”的长期社交组织系统。**

复盘时建议重点讲清三点：

1. 为什么公会要用 `GuildManager + Guild` 两层结构
2. 为什么申请审批链路和好友/组队邀请类似但更复杂
3. 为什么公会系统天然需要权限、职位和持久化三套能力
