## 1. 系统定位

聊天系统解决的是“玩家怎么发消息、消息如何按频道分流、UI 如何过滤显示”的问题。

它和好友、公会这类关系系统不同，更偏向消息流系统。

也就是说，它的核心不是维护玩家关系，而是维护：

- 频道
- 消息列表
- 显示过滤
- 发送目标

## 2. 核心数据结构与频道模型

### 2.1 ChatChannel 的作用

聊天系统最核心的定义是 `ChatChannel`，它区分了：

- 本地
- 世界
- 系统
- 私聊
- 队伍
- 公会

从设计上看，频道值采用 2 的幂次形式，因此天然适合做位运算组合过滤。

### 2.2 客户端的双频道概念

客户端 `ChatManager` 同时维护两套频道概念：

- `sendChannel`：当前发消息使用哪个频道
- `displayChannel`：当前 UI 正在看哪个标签页

这说明聊天系统把“发到哪里”和“显示什么”拆开了，这一点非常合理。

### 2.3 Messages 数组的意义

客户端 `ChatManager.Messages` 是一个 `List<ChatMessage>[]` 数组，索引对应本地 UI 标签。

它不是单纯的“每个网络频道一份消息”，而是：

> **每个显示标签维护一份自己应展示的消息集合。**

例如 `All` 标签会收下本地、世界、公会、队伍、私聊、系统等多种消息。

### 2.4 ChannelFilter 的意义

`ChannelFilter` 用位运算定义每个 UI 标签包含哪些消息频道。

核心判断逻辑是：

```text
(Filter & Channel) == Channel
```

这意味着：

- 频道分流不是靠大量 if-else
- 而是靠位掩码高效判断

这是当前聊天系统最有代表性的实现亮点之一。

## 3. 客户端发送与显示链路

### 3.1 发送链路

客户端发送消息的主链路可以概括成：

```text
UIChat 输入内容
  -> ChatManager.SendChat
  -> ChatService.SendChat
  -> NetClient 发 ChatRequest
```

### 3.2 发送前的本地校验

`ChatManager.SetSendChannel()` 在切换发送频道时会做权限判断：

- 发队伍频道前检查是否有队伍
- 发公会频道前检查是否有公会

如果不满足条件，会直接插入系统消息提示，而不是继续发请求。

这类校验虽然简单，但能明显减少无效发包。

### 3.3 私聊目标的处理方式

当用户在好友列表或公会成员列表中点击私聊时，会调用：

```text
ChatManager.StartPrivateChat(targetId, targetName)
```

这会：

- 设置 `PrivateID`
- 设置 `PrivateName`
- 把发送频道切到私聊
- 触发 UI 刷新

所以聊天系统把“当前私聊对象”也放进 `ChatManager` 统一维护，而不是交给 UI 自己记。

### 3.4 接收链路

客户端接收消息的主链路：

```text
服务端返回 ChatResponse
  -> ChatService.OnChatResponse
  -> 按频道调用 ChatManager.AddMessages
  -> 位运算分发到对应 Messages[]
  -> 触发 OnChat
  -> UIChat.RefreshUI
```

### 3.5 UIChat 的职责

`UIChat` 本身做得非常薄：

- 切换显示频道
- 读取 `ChatManager.GetCurrentMessages()`
- 管理输入框和私聊目标显示
- 点击玩家超链接时弹角色操作菜单

这说明：

> **UI 只是输入输出壳，聊天状态和过滤逻辑都在 Manager 中。**

## 4. 服务端消息处理链路

### 4.1 私聊与群聊的处理差异

服务端 `ChatService.OnChat()` 里最重要的分支就是：

- 私聊：直接转发
- 非私聊：写入消息池

### 4.2 私聊的处理方式

如果频道是 `Private`：

- 服务端先通过 `SessionManager.Instance.GetSession(toId)` 找目标玩家
- 如果对方不在线，直接返回失败
- 如果在线，就把消息放进对方响应，同时给自己回显一份

这是一种典型的：

> **点对点即时转发模型。**

### 4.3 群聊的处理方式

如果不是私聊：

- 服务端会把消息先交给 `ChatManager.AddMessage()`
- `ChatManager` 再根据频道写入：
  - `System`
  - `World`
  - `Local[mapId]`
  - `Team[teamId]`
  - `Guild[guildId]`

所以这是一种：

> **按作用域分类存储的消息池模型。**

### 4.4 增量读取的意义

服务端 `GetWorldMessages / GetLocalMessages / GetTeamMessages / GetGuildMessages` 都支持通过索引读取新消息。

这说明当前设计并不倾向于“世界消息一来就全服瞬时广播”，而是保留了按索引增量获取的能力。

这对大规模频道来说是更稳妥的设计。

## 5. 当前实现的边界与风险

### 5.1 私聊强依赖对方在线

当前私聊没有离线消息承接逻辑，对方不在线就直接失败。

### 5.2 聊天消息池没有看到明显淘汰策略细节

虽然 `GetNewMessages()` 会限制首次获取最大记录数，但消息池本身持续增长时，长期仍要关注内存占用和清理策略。

### 5.3 客户端展示是拼接整段文本

`GetCurrentMessages()` 会把当前频道所有消息重新格式化成一个大字符串。消息很多时，要关注 UI 文本渲染开销。

### 5.4 频道权限校验主要在客户端做了第一层

例如队伍、公会发言前的本地检查是有的，但服务端仍应继续做最终校验，否则客户端绕过限制后仍可能发出不合法请求。

---

## 6. 总结

聊天系统可以压缩成一句话：

> **客户端 `ChatManager` 负责频道状态与位运算过滤，`ChatService` 负责收发消息，服务端则对私聊走在线直推，对其他频道走分类消息池存储。**

复盘时建议重点讲清三点：

1. 为什么显示频道和发送频道要分开
2. 为什么频道过滤适合用位运算
3. 为什么私聊和世界/本地/队伍/公会频道不能用同一种分发模型
