## 1. 系统定位

任务系统在这套项目里不仅负责维护“玩家有哪些任务”，还负责把任务状态投影成 NPC 头顶或对话交互所需的状态。

也就是说，它至少有两层职责：

1. 管理玩家任务集合
2. 管理 NPC 视角下的任务状态

这也是为什么 `QuestManager` 会同时维护：

- `allQuests`
- `npcQuests`

### 1.1 主要参与者

#### 1.1.1 配置与模型层

**文件**：
- `Src/Lib/Common/Data/QuestDefine.cs`
- `Src/Client/Assets/Scripts/Models/Quest.cs`

`QuestDefine` 描述：

- 前置任务
- 接取 NPC / 提交 NPC
- 任务目标
- 对话内容
- 奖励内容

`Quest` 则把 `QuestDefine` 与 `NQuestInfo` 组合起来，变成客户端可直接展示的任务对象。

#### 1.1.2 客户端运行层

**文件**：
- `Src/Client/Assets/Scripts/Managers/QuestManager.cs`
- `Src/Client/Assets/Scripts/Services/QuesService.cs`
- `Src/Client/Assets/Scripts/UI/Quest/UIQuestSystem.cs`
- `Src/Client/Assets/Scripts/UI/Quest/UIQuestDialog.cs`

#### 1.1.3 服务端权威层

**文件**：
- `Src/Server/GameServer/GameServer/Services/QuestService.cs`
- `Src/Server/GameServer/GameServer/Managers/QuestManager.cs`

## 2. 核心数据结构

### 2.1 QuestDefine：描述任务规则

`QuestDefine` 里最关键的字段可以分成四类：

#### 2.1.1 接取条件

- `LimitLevel`
- `LimitClass`
- `PreQuest`

#### 2.1.2 流程节点

- `AcceptNPC`
- `SubmitNPC`

#### 2.1.3 目标与文本

- `Target1 / Target2 / Target3`
- `Dialog / DialogAccept / DialogDeny / DialogIncomplete / DialogFinish`

#### 2.1.4 奖励

- `RewardGold`
- `RewardExp`
- `RewardItem1/2/3`

这说明任务系统是典型的配置驱动实现。

### 2.2 Quest：客户端运行时包装

`Quest` 有两种构造方式：

- 传入 `NQuestInfo`：表示已接取或已有状态的任务
- 传入 `QuestDefine`：表示当前可见但尚未接取的任务

这也是为什么代码里会用：

- `Info == null` 表示可接未接
- `Info != null` 表示已接或已完成流程中的任务

### 2.3 QuestManager 的两层索引

客户端 `QuestManager` 的两个核心字段：

- `allQuests`：按任务 ID 管理所有当前有效任务
- `npcQuests`：按 NPC 分组管理任务状态列表

其中 `npcQuests` 又按：

- `Available`
- `Complete`
- `Incomplete`

继续细分。

所以它实际上不是单一列表，而是：

> **任务主索引 + NPC 查询索引**

## 3. 客户端任务组织方式

### 3.1 Init 的作用

`QuestManager.Init()` 接收服务器下发的任务列表后，会：

1. 保存 `questInfos`
2. 清空旧的 `allQuests`
3. 清空旧的 `npcQuests`
4. 调用 `InitQuests()` 重建任务状态

### 3.2 InitQuests 做了什么

`InitQuests()` 主要包含两步：

#### 3.2.1 先把已有任务装进去

对于服务端已经下发的任务：

- 构造 `Quest`
- 塞进 `allQuests`
- 同时为接任务 NPC 和交任务 NPC 建索引

#### 3.2.2 再补可接但尚未接取的任务

`CheckAvailableQuests()` 会扫描配置表，筛出满足条件但未进入 `allQuests` 的任务，例如：

- 职业符合
- 等级符合
- 前置任务满足
- 当前还没有接取

然后再把它们也放进 `allQuests` 与 `npcQuests`。

### 3.3 这套设计的价值

它让客户端同时拥有两种视角：

- 玩家任务列表视角
- NPC 对话交互视角

因此：

- 打开任务面板，可以看全部有效任务
- 点 NPC，可以快速知道它现在给什么任务状态

## 4. 任务接受与提交流程

### 4.1 接任务流程

客户端接任务主链路：

```text
玩家与 NPC 交互
  -> QuestManager.OpenNpcQuest(npcId)
  -> ShowQuestDialog(quest)
  -> 用户确认
  -> QuesService.SendQuestAccept(quest)
  -> 服务端 QuestService.OnQuestAccept
  -> 服务端 QuestManager.AcceptQuest
  -> 返回 QuestAcceptResponse
  -> 客户端 QuesService.OnQuestAccept
  -> QuestManager.OnQuestAccepted
  -> RefreshQuestStatus
```

### 4.2 提交任务流程

```text
玩家与 NPC 交互
  -> QuestManager.OpenNpcQuest(npcId)
  -> 命中可提交任务
  -> ShowQuestDialog(quest)
  -> 用户确认
  -> QuesService.SenQuestSubmit(quest)
  -> 服务端 QuestService.OnQuestSubmit
  -> 服务端 QuestManager.SubmitQuest
  -> 发放奖励
  -> 返回 QuestSubmitResponse
  -> 客户端 QuesService.OnQuestSubmit
  -> QuestManager.OnQuestSubmit
  -> RefreshQuestStatus
```

### 4.3 服务端任务管理器的职责

服务端 `QuestManager` 主要处理三类事情：

1. 接任务时创建角色任务记录
2. 提交任务时校验状态并更新完成状态
3. 发放金币、经验、道具奖励

这意味着任务是否真正完成，完全以后端状态为准。

## 5. NPC 任务状态机制

### 5.1 为什么要维护 npcQuests

单看任务列表，只能知道玩家当前有哪些任务；但 NPC 交互需要回答的问题是：

- 这个 NPC 有没有可接任务？
- 有没有已完成可提交任务？
- 有没有还在进行中的任务？

所以项目里额外维护了 `npcQuests`。

### 5.2 GetQuestStatusByNpc 的意义

`GetQuestStatusByNpc(int npcId)` 按优先级返回：

1. `Complete`
2. `Available`
3. `Incomplete`
4. `None`

这个优先级很合理，因为从玩家体验看：

- 可提交通常优先级最高
- 其次是可接任务
- 最后才是进行中提示

### 5.3 OpenNpcQuest 的意义

`OpenNpcQuest()` 的本质不是“打开任务列表”，而是：

> **根据某个 NPC 当前最重要的任务状态，决定弹出哪一个任务对话。**

这让 NPC 对话逻辑可以被统一封装在 `QuestManager` 中，而不是散落在 UI 或 NPC 交互脚本里。

## 6. 当前实现的边界与风险

### 6.1 状态刷新依赖整体重建

`RefreshQuestStatus()` 的方式是：

- 清空 `npcQuests`
- 更新或插入任务
- 重新跑 `CheckAvailableQuests()`
- 再次遍历 `allQuests` 建索引

这种实现优点是简单直接，但任务数量上来后，增量更新效率不高。

### 6.2 条件判断存在可读性风险

`ShowQuestDialog()` 中的这段判断：

```text
if (quest.Info != null || quest.Info.Status == QuestStatus.Complated)
```

从语义上更像是想表达某种“已接但未可提交流程”的逻辑，但这里用了 `||`，阅读时容易产生歧义，后续维护要特别小心。

### 6.3 Quest UI 刷新事件利用不充分

虽然 `QuestManager` 暴露了 `onQuestStatusChanged`，但当前 `UIQuestSystem` 没有明显完整订阅刷新链路，因此任务变化后界面刷新联动还不算特别集中。

### 6.4 奖励发放里经验逻辑还未完整展开

服务端 `SubmitQuest()` 中可以看到金币和道具奖励已处理，但经验逻辑目前是注释占位。说明任务奖励链路并未完全闭环。

---

## 7. 总结

任务系统可以压缩成一句话：

> **客户端 `QuestManager` 同时维护任务集合和 NPC 状态索引，`QuesService` 负责接提交流程通信，真正的任务生效与奖励发放都以后端 `QuestService + QuestManager` 为准。**

复盘时建议重点讲清三点：

1. 为什么 `Quest` 允许 `Info == null`
2. 为什么要维护 `npcQuests` 这层索引
3. 为什么任务系统本质上是“列表视角 + NPC 视角”双视图结构
