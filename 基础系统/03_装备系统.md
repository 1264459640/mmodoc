## 1. 系统定位

装备系统在当前项目里不是独立资产池，而是建立在道具系统之上的一层“装备槽视图”。

也就是说：

- 道具系统回答“你有什么装备道具”
- 装备系统回答“这些装备道具当前穿在哪个槽位上”

这点非常重要，因为它决定了后面整个实现方式。

### 1.1 主要参与者

#### 1.1.1 配置与模型层

**文件**：
- `Src/Lib/Common/Data/EquipDefine.cs`
- `Src/Client/Assets/Scripts/Models/Item.cs`

`EquipDefine` 负责描述：

- 槽位 `slot`
- 属性加成 `STR / INT / DEX / AD / AP / DEF / MDEF / SPD / CRI`

客户端没有单独的 `EquipItem` 类型，而是直接复用 `Item`，通过 `EquipInfo` 判断它是否为装备。

#### 1.1.2 客户端运行层

**文件**：
- `Src/Client/Assets/Scripts/Managers/EquipManager.cs`
- `Src/Client/Assets/Scripts/Services/ItemService.cs`
- `Src/Client/Assets/Scripts/UI/Eqyup/UICharEquip.cs`

#### 1.1.3 服务端权威层

**文件**：
- `Src/Server/GameServer/GameServer/Services/ItemService.cs`
- `Src/Server/GameServer/GameServer/Managers/EquipManager.cs`

## 2. 核心数据结构与引用共享

### 2.1 EquipSlot 决定装备栏结构

装备栏并不是字典，而是一个按枚举槽位索引的数组。

```text
Weapon / Accessory / Helmet / Chest / Shoulder / Pants / Boots
```

这种设计的优点是：

- 槽位固定
- 数组访问简单
- 序列化方便
- UI 对应关系清晰

### 2.2 EquipManager 的核心存储

客户端 `EquipManager` 的核心字段是：

- `Item[] Equips`
- `byte[] Data`

其中：

- `Equips` 负责运行时读取与 UI 刷新
- `Data` 负责与网络同步格式保持一致

### 2.3 最关键的设计：引用共享

从 `OnEquipItem()` 和 `ParseEquipData()` 可以看出，装备系统并不会创建一份新的装备对象，而是直接引用：

```text
ItemManager.Instance.Items[itemId]
```

这就是这套系统最核心的设计：

> **装备栏保存的是对道具系统中 Item 对象的引用，而不是复制一份装备数据。**

### 2.4 这种设计带来的好处

#### 2.4.1 避免重复数据

装备在背包和装备栏中本质上是同一个 `Item`，不用维护两份对象。

#### 2.4.2 属性天然一致

如果未来 `Item` 扩展强化等级、耐久、绑定状态等字段，那么：

- 背包看到的是这份数据
- 装备栏看到的也是同一份数据

不需要额外做同步。

#### 2.4.3 脱装备成本低

脱装备时只要把槽位引用清掉即可，不需要把某个新对象重新塞回背包。

## 3. 客户端穿脱装备链路

### 3.1 穿装备主链路

客户端穿装备主链路可以概括成：

```text
UICharEquip 点击装备
  -> EquipManager.EquipItem(item)
  -> ItemService.SendEquipItem(item, true)
  -> 服务端处理
  -> 返回 ItemEquipResponse
  -> ItemService.OnItemEquip
  -> EquipManager.OnEquipItem(pendingEquip)
  -> 触发 OnEquipChanged
  -> UICharEquip.RefreshUI
```

### 3.2 脱装备主链路

```text
UICharEquip 点击卸下
  -> EquipManager.UnEquipItem(item)
  -> ItemService.SendEquipItem(item, false)
  -> 服务端处理
  -> 返回 ItemEquipResponse
  -> ItemService.OnItemEquip
  -> EquipManager.OnUnEquipItem(slot)
  -> 触发 OnEquipChanged
  -> UICharEquip.RefreshUI
```

### 3.3 ItemService 在装备系统里的作用

虽然叫 `ItemService`，但它同时承载了装备通信：

- 发送 `ItemEquipRequest`
- 用 `pendingEquip` 暂存当前待处理装备
- 等服务端回包成功后，再通知 `EquipManager`

这说明当前装备系统不是事件总线驱动，而是：

> **请求 - 回包 - 本地更新** 的典型交互式流程。

### 3.4 UICharEquip 的显示逻辑

`UICharEquip.RefreshUI()` 会刷新三类内容：

1. 背包中可装备列表
2. 已装备槽位列表
3. 角色当前属性面板

其中有个关键细节：

- 背包装备列表会跳过 `EquipManager.Instance.Contains(kv.Key)` 为真的物品

也就是说：

> **已装备物品并没有从 `ItemManager` 消失，只是 UI 层不再把它显示在待装备列表里。**

## 4. 服务端装备权威处理

### 4.1 服务入口

服务端装备操作从 `GameServer.Services.ItemService.OnItemEquip()` 进入，再转到 `GameServer.Managers.EquipManager.EquipItem()`。

### 4.2 服务端 EquipManager 的真实行为

服务端实现非常直接：

- 检查该 `itemId` 是否存在于角色 `ItemManager.Items`
- 调用 `UpdteEquip()` 把对应槽位的 itemId 写入装备数据
- 保存数据库

这说明当前服务端装备系统的真实语义是：

> **装备栏记录的是“哪个 itemId 当前挂在哪个槽位上”，而不是把这个物品从角色资产里搬走。**

### 4.3 这和很多传统背包实现不一样

很多项目会在穿装备时：

- 从背包删掉装备
- 再往装备栏放一份副本

但当前项目不是这样做的，而是“同一资产，多种视图”。

这是你在讲项目时非常值得强调的实现特点。

## 5. 属性与 UI 联动

### 5.1 装备变化如何通知 UI

`EquipManager` 暴露了 `OnEquipChanged` 事件。

`UICharEquip` 在 `Start()` 中订阅，在 `OnDestroy()` 中取消订阅，所以装备变化后界面可以自动刷新。

### 5.2 装备变化为什么能影响属性面板

`UICharEquip.InitAttributes()` 最终读取的是：

```text
User.Instance.CurrentCharacter.Attributes
```

这意味着装备展示和属性展示在 UI 上是一起刷新的。虽然当前片段里没有展开整套属性重算过程，但从使用方式看，装备系统最终会体现在角色属性读取结果上。

### 5.3 槽位 UI 的优势

由于 `Equips` 本身就是固定槽位数组，所以：

- UI 插槽和数据槽位是一一对应的
- 不需要复杂查找
- 初始化已装备列表时只需按索引遍历

## 6. 当前实现的边界与风险

### 6.1 pendingEquip 一次只支持一个请求

客户端 `ItemService` 里用 `pendingEquip` 控制并发，这意味着：

- 当前同时只能有一个装备请求在途
- 如果用户短时间连续点击，后续请求会直接失败

这种方式简单，但扩展性一般。

### 6.2 客户端成功更新依赖回包

只有服务端返回 `Result.Success` 后，客户端才会调用 `OnEquipItem` 或 `OnUnEquipItem`。这保证了一致性，但也意味着弱网下 UI 反馈会滞后。

### 6.3 服务端没有更细粒度校验

从当前代码看，服务端主要校验“物品是否存在”，但没有在这一层看到：

- 职业限制校验
- 槽位与装备类型匹配校验
- 重复装备约束校验

如果这些逻辑已经在其他层处理还好，否则这里是潜在风险点。

### 6.4 文档表述要避免误导

讲装备系统时最容易说错的一点是：“穿装备时物品会从背包移除”。

结合当前代码，更准确的说法应该是：

- 物品仍在资产集合中
- 装备栏记录了该物品当前是否处于某个槽位
- UI 决定它显示在待装备区还是已装备区

---

## 7. 总结

装备系统可以压缩成一句话：

> **`EquipManager` 不是独立物品仓库，而是基于 `ItemManager` 的装备槽位视图，核心设计是通过共享同一个 `Item` 引用来避免重复数据。**

在复盘或面试里，建议重点强调：

1. 为什么不用复制装备对象
2. 为什么当前实现适合做属性一致性维护
3. 为什么 UI 过滤已装备物品比迁移数据更简单
